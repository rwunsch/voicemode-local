Another WSLg data point, from a Win11 + WSL2 machine that has been running voicemode daily for a few months. One observation we found useful: on our machine "crackling on WSL" turned out to be several causes with the same symptom, and fixing one did nothing for the others. In case it helps anyone bisecting:

**1. The streaming path plays each PCM chunk the moment it arrives, with no pre-roll.** (Checked in the code against current `master`, 126d15e.) `stream_pcm_audio` opens an `sd.OutputStream` with default latency and calls `stream.write()` on every received chunk ([streaming.py#L462-L466](https://github.com/mbailey/voicemode/blob/126d15e021217983bd353501285859e1195a3cb9/voice_mode/streaming.py#L462-L466)). On WSLg's RDP sink, any late chunk means an underrun right away. Interestingly, `STREAM_BUFFER_MS` (default 150, "Initial buffer before playback") is imported into `streaming.py` but never read, and `buffer_underruns` is declared but never incremented. So the pre-roll looks designed but never wired up.

- *What we measured:* `paplay` of a pure tone through the same sink played clean while voicemode stuttered at the same moment, so WSLg itself was healthy. Setting `VOICEMODE_STREAMING_ENABLED=false` (it needs an MCP restart) made the stutter go away for us.
- *Inferred:* that's probably also why the `paplay` workarounds above help. They play a complete buffer instead of streaming.
- *Suggested small fix:* actually honour `STREAM_BUFFER_MS` by holding back that much audio before the first `write()`.

**2. Load-induced stutter that clears up by itself.** WSLg's audio transport runs outside the distro, and as far as we could tell it can't be pinned or prioritised from inside it (`perf` doesn't reach it either). With several agent sessions open at once, our load hit ~13 on 12 cores and playback stuttered, then recovered as load dropped. A CPU-only Kokoro on the same box made it worse; moving Kokoro to the GPU (or capping its CPUs) removed that part. *Inferred* from correlating load with stutter episodes, not proven. The self-clearing behaviour is worth knowing about, though, because it makes you go looking for a race that isn't there.

**3. A duplicate voicemode process still holding the sink.** If the MCP server is shut down mid-playback (reconnect, cancel), the PortAudio host thread can keep the old process alive. You then have two processes with sink-inputs on the same RDP sink, which sounds like mixing or stutter. Quick check: `pgrep -af voice-mode` (more than one per session is the tell) and `pactl list sink-inputs`. 8.12's shutdown patch cancels in-flight handlers, but nothing forces the process to exit while an audio thread holds it open.

(A separate one that also *sounds* like an audio bug, two Kokoro servers fighting over :8880, is filed as #534.)
